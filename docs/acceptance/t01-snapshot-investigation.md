## Source evidence and coverage limits

Unmapped legacy forms and remote objects must be explicitly accounted for, not silently omitted.

The schema owners also include processing jobs, pipeline runs, settings, deliveries, media intents and receipts. A complete backup must retain their bytes and relationships, including unfamiliar tables; counting selected rows is insufficient. Database and file snapshots also need a defined consistency boundary when files change while a live SQLite backup runs.

## Developer interface and boundaries

Run `python3 scripts/io_snapshot.py snapshot DATABASE DESTINATION --root vault=VAULT` and supply `--root private_raw=PRIVATE_ROOT` and `--root paper_images=IMAGE_ROOT` when needed. Additional explicit roots can overlap: logical roles bind to subtrees of one stored physical tree. `verify SNAPSHOT` and `restore SNAPSHOT DESTINATION` are separate commands; the corresponding Python functions are public. The parent must exist, destination must not exist, and no source may overlap the destination or database. The snapshot and manifest contain private data and filenames, so keep them private. Console output does not include content, credentials or paths.

The database is read through SQLite's online backup; snapshots preserve arbitrary tables and rows without translating them. Snapshot creation and verification require the version-41 tables, columns and safety invariants in `scripts/io_schema41.json` and `scripts/io_schema41_semantics.json`. Both self-contained descriptors come from the empty 71-table fixture and have pinned SHA-256 values; missing or damaged descriptors fail closed. SQLite metadata verifies primary keys, canonical explicitly NOT NULL columns, unique keys and foreign keys. CHECK expressions and partial-index predicates are compared as normalized SQL tokens, preserving literal values. Required unique indexes may have a different name or column order when their key and predicate are equivalent; unknown extra tables, columns and indexes are preserved. The gate ignores SQL whitespace and does not infer NOT NULL from a nullable canonical primary key. Logically equivalent CHECK or predicate rewrites beyond normalization can be conservatively refused; historical schemas outside this contract remain unsupported. Verification also checks integrity, foreign keys, schema, table counts and content hashes, version markers and asset hashes. Literature mappings are checked against `vault`, private Raw against `private_raw`, including file hash, size and owner identity. Database version text hashes and available authority mappings are checked. Format 4 stores original root names and paths and per-reference bindings; those paths are private evidence. `read_asset(restored_directory, table, column, identity)` resolves bound bytes against the restored tree and checks their hash without consulting the original roots or rewriting historical database fields. Development formats 1–3 are refused; this implementation does not upgrade them.

`recovery_binding` returns the currently checked path, SHA-256, size, device and inode; `read_recovery_asset` reopens and checks those values. `recovery_adapter` produces ephemeral staging fields for IO's document/preimage recovery without changing the stored audit row. The consumer must reopen with no-follow, require a regular single-link file, compare device/inode, size and hash immediately before use, and retain IO's existing conditional target-write checks. Binding evidence is not permission to overwrite a changed target and cannot eliminate a later race.

Bindings cover unmapped absolute Raw files, literature and private Raw mappings, literature archive sources, pending media payloads, media-document staging, activation quarantine and preimage, ingestion failure artifacts, reading/news notes, legacy cleanup-media recovery, and cleanup backups. Cleanup backup manifests and each listed body/draft are checked against their recorded hashes and counts. Source HTML gzip payloads are checked against the uncompressed hash; nested retained image archives use their own `file_hash`. The ported source image inventory handles inline/reference Markdown, Obsidian embeds, HTML image attributes/srcset and code masking; local targets resolve against the mapped vault document or, for database text without a document path, the explicit `paper_images` role. Unsupported or unresolved inventory entries fail closed. An explicit reviewed alias list can be supplied as `snapshot(..., image_aliases=[...])` or `--image-aliases JSON_FILE`; aliases bind occurrence/target, exact document SHA-256, owner Raw document and evidence, shared-pool path and expected source hash. Existing direct images take precedence, and filename guessing is forbidden. Alias evidence is retained privately in the manifest.

The manifest records schema fields containing `path`, `_root` and `_json`, their handling classification, and each recognized binding; unknown populated path fields are rejected. For current source owners it also explicitly marks body/draft text as image inventory, retained-image JSON, remote object URL/hash, database upload-intent payload, media pending `source_ref`, and remote media usage `source_ref`. JSON is recursively scanned for path and root keys, and unbound roots or missing files are rejected. `legacy_content_imports.path` is historical ledger evidence, not a claim that an old path is currently readable. A prepared, absent quarantine is recorded as a reservation; cleaned staging remains a tombstone, while reset-retired staging bytes remain required as specified by the source owner. Each nondeleted managed remote object requires locally preserved bytes matching its stored SHA-256 and size, in an included asset root or its own upload-intent BLOB. Remote-only metadata is refused. `remote_references` identifies objects requiring later live readback; matching local bytes do not prove the remote object is currently readable. Earlier remote-only success behavior was superseded by the round-one Spec fixes. The manifest's hashes are not signatures: an attacker who changes both data and manifest can forge self-consistent evidence. Independent restore tests query known synthetic values directly rather than trusting the manifest alone.

The operation inventories roots, copies the source database and its existing WAL as ordinary read-only files into a private staging directory, and takes an SQLite online backup from that private copy. It repeats the observation and backup after copying assets. Source main, WAL and existing SHM are hashed and checked for stable identity, metadata and bytes around each copy and across both observations. SQLite never opens the live source; it regenerates any required SHM only inside private staging. WAL frame structure and checksums are validated before recovery. A stable, checksummed source WAL index proves the last committed frame and distinguishes a normal reused WAL's stale tail; the copied SHM is evidence only and is never given to SQLite as coordination state. If no source SHM exists, the WAL must be self-consistent without relying on a stale-tail index. Rollback journals, unsafe sidecars, unindexed frames and observed source changes are refused. Earlier mode=ro behavior could create or modify source SHM and is superseded. The online backup itself is bounded to 10 seconds. This is a conservative stability check, not an atomic transaction across SQLite and files: changes that occur and revert between observations are not detectable. Quiesce writers and use independent trusted evidence before any real migration.

Publication reserves an absent destination and moves staged entries into it. A crash can leave an incomplete reserved destination; verification rejects it, and a retry never overwrites it. Remove or inspect such a directory manually only after confirming ownership. Symlinks and special files in asset trees are rejected, with no-follow file-descriptor traversal. This is not a hardened defense against an adversary concurrently replacing source database or parent directory paths.
