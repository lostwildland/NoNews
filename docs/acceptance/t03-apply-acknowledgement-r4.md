# T03 Apply acknowledgement R4 correction

Correction starts at a8f3d21627ac685e69870176382dd860da53cad4. The coordinator owns this small three-source-file change; the original implementation owner retains the backend storage work. A source-boundary steer was delivered before editing.

R4 found that an Apply response could be displayed on another service's newer report, manual Preview erased confirmed Apply acknowledgement, and historical waiting could contradict a refreshed active-claims report. These are source-derived independent-review findings, not observed GUI failures.

Apply requests now have their own generation and immutable migration input. The shared review state retains only a matching latest Apply response, tags its acknowledgement with that input and leaves it intact when a preview starts or fails. The controller publishes it only when the selected input still matches. A service change clears the previous report's display and pending-job controls. Waiting acknowledgement describes the earlier Apply; the newly read report supplies current pause/running facts. Unknown Apply status does not create a successful acknowledgement.

The existing public MigrationReviewState check is the regression seam. Before the fix, a compiled executable exited1 with `FAIL: historical Apply acknowledgement claims a current pause`; it exited normally rather than crashing the host. After the correction the executable passes checks for A responding while B is previewed, B's newer Apply superseding A, repeated failed readback retries preserving A's confirmed result, historical waiting alongside current active claims, unknown responses and distinct same-name service labels. This constructs state only, without an engine or app instance.

The actual final engine and preferences sources also passed a narrow Swift6 arm64/macOS15 typecheck with warnings treated as errors and no diagnostics, including the shared reset of routing choices/report controls for both service selection and New Service. It reused accepted T02 compiled dependencies with temporary Clang maps pointing to their matching headers; source/maps/private cache were removed afterward. A full target build and actual UI response wiring remain required.

Separately, root extracted the committed a8f3d2 ManagedEngine tree and independently ran the authenticated greater-than16MiB report test under system Python, bytecode disabled and ResourceWarning as an error: one test passed in2.644seconds. This verifies report readback/retry/restart/coherence and failed-publication preservation. It does not prove bounded Apply/evidence memory, bounded native browsing, a general request-time or RSS bound, or the packaged runtime. Those later slices, fresh paired correction review and full T03 acceptance remain open.
