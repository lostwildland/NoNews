# Managed jobs read

`GET /api/jobs` accepts an optional `query` object containing only `cursor`. The first request uses `{}`. Each authenticated reply has the request `id` and a `result` containing `chunk` (base64 bytes), `recordComplete` and `next` (opaque cursor or null). Decode and append chunks in order; when `recordComplete` is true, decode the accumulated UTF-8 JSON object and clear the buffer. Continue with `query: {"cursor": next}` until `next` is null. An empty history returns an empty chunk, `recordComplete: false`, `next: null`. Each chunk holds at most 24,000 bytes, even when a job contains very large Unicode strings. Records use the existing jobs fields, error resolution and settings-scope retry semantics; no returned field is truncated. The raw `result_json` field is included unchanged so large stored results remain retrievable through the private channel.

Order is descending SQLite job rowid. Continuations carry the rowid, byte offset and SHA-256 of the serialized record, and a changed or removed record is rejected as `invalid query`; restart enumeration on this error. The interface is not a snapshot across requests: later inserts above the first cursor are not included, and deleted or edited jobs can require restarting. Do not interpret the cursor as a job ID or construct it yourself. The private channel authenticates requests and bounds every message to 65,536 bytes. Unknown query keys and malformed cursors are rejected before dispatch. Future Activity callers own cancellation, display and any history refresh policy.
